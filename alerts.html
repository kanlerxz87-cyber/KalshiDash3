Live alert chats — swings ≥ $0.10 in either direction

Two scrolling chats of real-time contract-price alerts on the Kalshi demo exchange: all events and a filtered feed of events the model likes as high-ROI candidates. An alert fires whenever a watched contract moves ≥ $0.10 between two consecutive observations, up or down. The engine polls the public demo API from your browser and, when that is not possible, falls back to the collector's committed price history — every alert is labelled with its origin.

Alert threshold ($0.10, both directions): this project's stated requirement — it is not an API field. Live detection polls GET /markets?tickers=…, which returns every matching market in one response when tickers is the only filter (Get Markets). Kalshi documents that REST responses are cached briefly, so prices can lag the exchange by seconds — polling faster than that cannot add information. Unauthenticated requests have separate rate limits; the engine backs off exponentially on HTTP 429 (Rate Limits). Without live REST, the chats replay the collector's committed history (scripts/build_alerts.py → data/live/alerts_archive.json, an append-only archive, so swings survive a market closing). "News leads" links are search queries computed from the market title, not verified causes — the archive keeps cause_link null by design and causality is never asserted (see F-15, F-25).

Was it a trade, or only a quote? The alert rule watches last_price_dollars, which Kalshi defines as the price of the last traded contract (Get Markets). Two reads of that field can be ≥ $0.10 apart with no trade at all in between, so each alert now carries the contracts actually traded between its two observations — the difference of the cumulative volume_fp field across those reads. Alerts are chipped traded (at or above this project's floor), thin (some contracts, below the floor), no trades (zero contracts — the printed price changed on its own), volume n/a (the cumulative field did not increase across the reads, so the count is unknowable and is left blank), candle-sourced (the swing is bounded by a candle-backfill read, whose volume_fp is a per-period count rather than a cumulative one, so differencing would invent a number) and no history (the two observations are no longer in the committed history). The floor is a project rule, not a Kalshi field — Kalshi publishes no per-move significance field — and every alert shows the exact contract count so you can apply your own. Full method: scripts/alert_evidence.py; F-79, F-80, F-81.
Was the move even in the book? The rule watches last_price_dollars, the last traded price, while yes_bid_dollars / yes_ask_dollars are the two-sided quote read in the same Get Markets response (documented as cached, so the quote can lag the exchange by seconds). Each alert therefore also compares its printed end price with that quote: print ≠ book means the price printed outside the recorded bid/ask band, so the move was not available at the quote a reader could have traded, and the chip states by how much. Rows that carry no usable quote are counted as quote unknown and nothing is inferred. This is a per-row comparison of two official fields, not a re-scoring of the model screen (F-121; the demo oscillation itself is F-77).

Tracked to resolution — how the events behind these alerts settled

The collector follows alerted contracts even after they leave the rankings. It uses Kalshi’s current and historical market records. A result is final only when the market is finalized; a determined or disputed result is not yet a payout (Market Lifecycle). If a lookup is unavailable or deferred, the result stays blank and the status is marked unverified.

How the model pick is computed (fully disclosed)

Membership is one rule on every page. A swing is a model pick when the canonical archive's frozen high_roi flag is set for it: its series is in the official fee schedule (fee schedule — the confirmed basis) and the market reported positive 24-hour volume at the moment the swing was detected. The flag is written once by scripts/build_alerts.py from data/alert_rules.json and never relabelled, so the dashboard, this page and the chat dock show the same count. A live swing this browser detects before the archive has seen it is judged by that same rule.

The heuristic score 0.30×liquidity + 0.25×price-band + 0.30×momentum + 0.15×spread (each 0–1) is still printed on each pick as a ranking hint, and it is not the inclusion rule. Until 2026-11-22 it was: that made the three surfaces disagree (49 dashboard / 47 here / 46 in the dock, over the same 61 alerts), which is a defect, so it is recorded as D-02. The score itself has never been backtested and is flagged (F-26). This is an experimental screen, not advice.

Category tabs filter both chats. Categories stay separate — a market is attributed to one topic only: by the exchange's own series classification (GET /series?category=…, F-66), by a fee-schedule-confirmed series (confirmed), or by a flagged keyword match (keyword).

Fetched source leads beside each recorded swing

One row per swing in the persistent archive (data/live/alerts_archive.json, threshold $0.10). A "lead" is the reference the market itself settles on — quoted from its own record — next to the published numbers that reference carried when it was fetched. No link here is a proven cause: Kalshi has no cause feed, and a public quote cannot see the trade that printed a price. Where the reference did not move in the same minutes, the row says so. Built by scripts/catalysts.py from the review ledger data/catalyst_review.json; each link was fetched and read, with its fetch time.
